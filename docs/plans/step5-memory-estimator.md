# Step 5 — Model Memory Estimator: final technical plan

Status: final, agreed with the owner's mandatory corrections (2026-11-01).
Scope: MVP only. Step 6, CHAIN-SPLIT and automatic memory management are out of scope.

## Decisions that answer the corrections one by one

| # | Correction | Decision in the plan |
|---|------------|----------------------|
| 1 | Three memory quantities per model | `model_memory.json` card holds `storage_size_mb`, `estimated_loaded_weights_mb`, `estimated_runtime_peak_mb`; each value is a block `{value, source, confidence, estimation_method, last_verified, caveats}`. File size is never copied into the loaded-weights field automatically. Unknown → `value: null`. No coefficients are invented: the only file-size-to-memory assumption (quantized containers) is labelled `low` confidence and `assumed_equal_to_file_size`. |
| 2 | History is not exact attribution | `history.py` normalises every ledger row into an observation with MemAvailable before / min / after, system used peak, cgroup before / peak / after, Studio RSS, concurrency, lane, both revisions and the sample count. Runs with `concurrency > 1` go into a separate `mixed` bucket and never calibrate. Sampling interval is carried through and a gap between samples downgrades confidence. Telemetry values are read, never rewritten. |
| 3 | Partial estimates | Result carries `known_components_mb`, `partial_estimate_mb`, `unknown_components[]`, `coverage_percent`, `expected_mb`, `upper_bound_mb`. `expected_mb`/`upper_bound_mb` are `null` whenever coverage < 100 % and no comparable measurement exists. Status `partial` explains the missing piece by name. |
| 4 | Risk and confidence are independent | `risk_level` (low / moderate / high / unknown) is computed only from headroom against MemAvailable. `confidence` (low / medium / high / insufficient_data) is computed only from coverage, sample count, spread, revision match and counter availability. The word `unsafe` is not used anywhere in the contract or the code. Both reason lists are always returned. |
| 5 | Host lane in MVP | Whisper (`asr-large`) and VLM (`vlm-caption`) are first-class. Their memory is per-process and is read from what the telemetry already sampled; system and process counters are never summed. |
| 6 | Model catalog file | `studio/registry/model_memory.json` is generated by `python -m app.memory.catalog --write`, sorted and deterministic apart from `generated_at`; parser version, sha256 (from the curated catalog, never recomputed silently), source, confidence and `last_verified` per value. Hand edits are overwritten by design. |
| 7 | Calibration | MVP uses only existing telemetry. `studio/backend/tools/memory_calibrate.py` compares prediction with fact leave-one-out; it opens the database read-only, refuses to run workflows and is not reachable from the API. |
| 8 | Architectural limits | No DB schema change, no migration, no `jobs.py` or dispatch change, no admission wiring, no engine calls, no GPU settings, no heavy workflows, no outbound network. API is read-only and behind the existing auth. |
| 9 | Sequence | git state → modules/tests → catalog → analyzer → profiler → estimator → API → calibration CLI → tests → docs → full regression → production check. |
| 10 | Done criteria | All existing tests green, coverage ≥ 76 %, no migration, no dispatch change, no engine action, no double counting, unknown components handled, owner isolation proven, catalog reproducible. |

## Estimation algorithm

1. **Fingerprint** = `workflow_id` + `graph_revision` + `lane` + parameter bucket (frame area, frame
   count, batch). Revision mismatch means history is not transferable.
2. **Analytic part**: one `model_load` component per referenced model, valued from the catalog's
   `estimated_loaded_weights_mb`. `runtime_overhead` is a component with `value: null` unless a
   measurement for the fingerprint exists — it is measured per workflow, not derived from a guess.
3. **Measured part**: for isolated runs of the same fingerprint, `measured_delta =
   system_used_peak − (MemTotal − MemAvailable_first)`; median and MAD give `expected` and
   `upper_bound` (p90, at least median + 2·MAD).
4. **Budget**: `budget = MemAvailable − reserve_mb`, `headroom = budget − expected`. Risk: `low`
   when headroom ≥ 25 % of expected, `moderate` inside 0…25 %, `high` below zero, `unknown` when
   expected is null or MemAvailable is unavailable.
5. **Refusal**: coverage < 100 % and no comparable measurement → `expected_mb: null`,
   `status: "partial"`, unknown components named, `recommended_action: "estimate_unavailable"`.

## API (read-only)

## Testing

`test_memory_catalog.py`, `test_memory_analyze.py`, `test_memory_history.py`,
`test_memory_estimate.py`, `test_memory_api.py` — unit tests on synthetic files and ledgers, an
explicit double-counting invariant, unknown-node and unknown-model cases, owner isolation, and a

## Risks accepted for the MVP

* Only 8 ledger rows carry memory; most workflows will report `insufficient_data` until calibration.
* `memory_peak_mb` is a window peak, so only `concurrency = 1` rows calibrate.
* Sampling every 0.5 s can miss a sub-second spike; the sample count is part of confidence.
* fp8 weights may be upcast at load time; the card says so in `caveats` and keeps confidence low.

## Final architecture

```
workflow definition ──► analyze.py ──► components (known MB, unknown names)
                                            │
studio/registry/model_memory.json ──────────┤
                                            ├──► estimate.py (pure) ──► verdict
job_telemetry ledger ──► history.py ────────┤        ▲
                                            │        │
/proc/meminfo + cgroup + sysfs ──► probe.py ┘        │
                                                      │
                        router.py (read-only HTTP) ◄───┘
```

Three quantities stay separate end to end: file size (must), loaded weights (estimate with a stated
method), runtime peak (a property of the workflow, never derived from a file). History contributes a
*measured delta* — `system_used_peak − (MemTotal − MemAvailable_first)` — which is an observation of
the whole machine during the run, not an attribution of bytes to a workflow.

## Catalog generation and reproducibility

`cd studio/backend && ../.venv/bin/python -m app.memory.catalog --write` produced
`studio/registry/model_memory.json`: 23 files — 10 safetensors, 7 ONNX, 2 torch pickle, 2 GGUF, 2 GGML.

* `storage_size_mb`: `high` for all 23 (a `stat` is a fact).
* `estimated_loaded_weights_mb`: 9 `medium` (dtype sum from a safetensors header), 5 `low` (quantized
  containers, where the dtype sum is a lower bound), 9 `insufficient_data` (7 ONNX + 2 torch pickle —
  `null`, not a guess).
* `estimated_runtime_peak_mb`: `insufficient_data` for all 23 by design — a peak belongs to a workflow.
* sha256 present for 19 of 23, taken from `studio/registry/models_catalog.json` and labelled
  `sha256_source`; the 4 without it stay `null`.

Two consecutive builds are identical in content and differ **only** in `generated_at` and
`last_verified`; with the timestamps stripped the canonical hash is `2e54aa4f…` on both builds. The file
is therefore not byte-reproducible across minutes — saying it were byte-identical would overstate it.
A test pins exactly that (`test_two_builds_differ_only_in_timestamps`), plus one that the `roots` block
stays relative to the project instead of embedding an author's home directory.

## Calibration: what the numbers do and do not say

`tools/memory_calibrate.py` over production `job_telemetry` (read-only, `mode=ro`):

* **8 observations** carry memory data;
* **8 analysed** — every one matched a workflow definition, its revision and its lane;
* **4 forecastable** (history produced a number): 2 × `vlm-caption`, 2 × `img-thumb-320`;
* **4 scored** (predicted and measured both present); `asr-large` and `sam-layer-split` produced an
  actual but no prediction, because their analytic components are partly unknown;
* **2 significant in magnitude** (≥ 100 MB) — both `vlm-caption`, within ±6.7 % of the measurement;
* MAE 23.7 MB, MAPE 6.5 % — **these two numbers describe those two observations and nothing else**.

The limits are real:

* These results do **not** establish general estimator accuracy. Two runs of one host workflow are a
  smoke test that the plumbing is right, not a validation of the model.
* Every comparable row has `basis: unproven_concurrency`, because the ledger's `concurrency` block
  stores service-level high-water marks rather than per-run occupancy. Confidence is therefore capped
  at `low` everywhere, by design.
* **No WAN, SDXL or SAM calibration runs have been performed.** Any claim about them would be invented.
* The two small `img-thumb-320` runs (8 MB and 29 MB measured) are excluded from percentages by the
  100 MB significance threshold; their absolute error is reported instead.

## Controlled calibration proposal (needs approval; nothing started)

Purpose: move from `unproven_concurrency` to evidence, with the smallest possible cost. Each scenario is
two sequential runs, one job at a time, Studio queue empty, no other work on the machine, 0.5 s sampler
unchanged, `generated_at` and revisions recorded.

| # | Workflow | Lane | Why this one | Cost per run |
|---|---|---|---|---|
| 1 | `vlm-caption` | host | already has 2 runs; a third pair turns a single point into a spread and tests revision stability | tens of seconds |
| 2 | `asr-large` | host | Whisper is the other host path; it is the one that competes with GPU jobs for `MemAvailable` | ~1 min |
| 3 | `upscale-realesrgan` | graph | real render (59 s) with a small model — a cheap test of the analytic component against a measured peak | ~1 min |
| 4 | `style-anime` (SDXL turbo, 4 steps) | graph | checkpoint-class model, seconds per run; gives the first non-host data point | ~seconds |

WAN 2.2 (`video-t2v-wan22`) is a **separate, longer test** (26 min, 9.5 GB diffusion model + 6.4 GB text
encoder) and will not be run without its own explicit approval.

Acceptance for the calibration set: for each scenario, `basis` becomes `isolated`; the median measured
delta and the analytic known-components figure are reported side by side, with the difference labelled
as runtime overhead — measured, not assumed. Success is not "the forecast matches"; it is "the spread
across runs is small enough to state a number, and the overhead is now a measurement".
