# TECHNICAL DEBT — comfyui-strix-halo

Phase 0 deliverable. Each item is grounded in a file/line or a command output. Nothing here is a
generic "would be nice"; every entry states what breaks if it is ignored.

Severity: **P1** = blocks the next phase; **P2** = cost grows with every feature; **P3** = hygiene.
Effort: **S** ≤ 1 day, **M** 2-3 days, **L** ≥ 1 week (one senior dev, this codebase).

---

## P1 — blocks Phase 1/2

### TD-1 · Three documents disagree with the code (auth, bind policy, test totals)
* **Evidence**: `PROJECT_SUMMARY.md:103` says LAN bind is refused; it is supported behind auth
  (`config.check_bind:174`, `docs/stage_net1_audit.md`). `implementation_status.md:206` item 11 says
  "single user, no authentication"; `auth.py` (430 lines) + `test_auth.py` (40 tests) say otherwise.
  Test totals read 289 (`README.md:50`), 200 (`implementation_status.md:19`), 192 (`:79`).
* **Why it hurts**: the docs are the onboarding path for a human *and* for an agent. A stale
  "no authentication" note invites re-implementing auth; a stale "no LAN" note invites re-opening a
  closed design decision. This is the cheapest fix in the whole audit.
* **Task**: rewrite the three sections from source; add a `docs/STATUS.md` generated by a script
  (`tools/gen_status.py`) that prints commit, test count, workflow/tool/model counts, so no human
  edits numbers again.
* **Effort**: S. **Risk**: none.

### TD-2 · `api.py` is one 1 110-line function with 43 route closures
* **Evidence**: `create_app()` at `api.py:82`; routes defined inline; all state reachable as closures.
  Grew from 958 lines / 34 routes to 1 110 / 43 in Phase 1 (revisions + telemetry + benchmark), which is
  exactly the trend this entry predicted.
* **Why it hurts**: every new endpoint (scheduler, benchmarks, models, hardware) lands in the same
  scope, and every test needs the full app with all dependencies. Per-domain routers
  (`routers/workflows.py`, `routers/jobs.py`, …) with explicit dependencies are a prerequisite for
  Phase 1-4 without merge pain.
* **Task**: extract routers one domain at a time (workflows → jobs → models → maintenance → auth),
  keeping URL paths and payloads byte-identical; the existing `test_api.py` (29) is the regression net.
* **Effort**: M. **Risk**: low (mechanical), but do it in ≤5 commits with tests green after each.

### TD-3 · No resource model — nothing knows whether a job fits
* **Evidence**: queue decisions use depth + per-user caps only (`config.py:46-52`, `jobs.py`).
  `ComfyClient.free()` (`comfy.py:229`) has zero callers. `min_vram_gb` is a static authored number.
* **Phase 1 measurement (2026-10-31)**: during the 1601.5 s WAN 2.2 render
  `mem_info_vram_used` reached **90.3 GB** on a **30.5 GB** machine while `MemAvailable` never fell
  below **19.15 GB**. So neither the static `min_vram_gb` nor the surfaced `vram_used` describes
  residency: the estimator must be calibrated on `MemAvailable` deltas from the run ledger
  (`docs/REFERENCE_RUNS.md`), and any gate built on `/system_stats` vram would never fire here.
* **Phase 1 step 3 (2026-11-01)**: the measurement half now exists — `job_telemetry` records
  `MemAvailable`-derived used/peak/available for every run (`docs/EXECUTION_TELEMETRY.md`). What is
  still missing is the *model*: nothing yet turns those rows into a prediction for a workflow that has
  not run on this machine. The ledger is the training set, not the estimator.
* **Why it hurts**: this is the single feature the brief calls "critical" (§10) and the one that makes
  WAN 2.2 (≈27 min, ~20 GB) co-exist with studio work safely. Without estimates, the only safe policy
  is strictly serial — which then wastes the 82 CPU-only host tools.
* **Task**: (a) a `resources.py` that samples `/system_stats` + `/proc/meminfo` before/after a job and
  stores peak deltas; (b) an estimator that learns per workflow from that history, and starts from the
  authored `min_vram_gb` as a prior; (c) a scheduler gate: refuse/pre-defer a job whose estimate exceeds
  free memory, and call `/free` only between jobs, never during one.
* **Effort**: L (honest estimate: 1.5 weeks with tests). **Risk**: medium — must never unload a model
  in use; keep the first version advisory-only (warn, do not block) behind a setting.

### TD-4 · Serial worker punishes the 82 CPU-only capabilities
* **Evidence**: `_worker_loop` (`jobs.py`) runs `_run_job` one at a time; host tools run via
  `asyncio.to_thread` (`jobs.py:498`) which is already parallel-capable. `DOC` 1 610.6 s for one WAN
  49-frame clip.
* **Why it hurts**: a 2-second thumbnail queues behind a 27-minute video render. That is a product
  defect users notice immediately.
* **Task**: two lanes — `gpu` (strictly serial) and `host` (bounded pool, default 2, configurable) —
  with a shared queue order and one cancellation surface. ComfyUI still never runs concurrently.
* **Effort**: M. **Risk**: medium — must preserve per-user caps across both lanes and keep
  `reconcile_orphans` semantics.

## P2 — cost grows with each new feature

### TD-5 · `hosttools.py`: 1 296 lines, flat dict, no tool metadata
* **Evidence**: `TOOLS` dict (34 keys, counted statically) + per-tool path constants + `_run` guard.
* **Why it hurts**: a 35th tool edits the same file that holds GPU-adjacent logic; nothing declares
  cost, inputs, outputs, or category, so a scheduler (TD-3) cannot reason about a tool without
  hardcoding its name.
* **Task**: split into `hosttools/{ffmpeg.py,audio.py,vision.py,docs.py}` behind a `ToolSpec`
  dataclass (`name, kind, cost_class, params_schema, run`). Registry stays one dict.
* **Effort**: M. **Risk**: low if done file-by-file with `test_hosttools.py` (14) as the net.

### TD-6 · No LLM/agent layer at all, while the brief assumes one
* **Evidence**: `grep -i "openai|anthropic|ollama|llm"` over `app/` matches only llama.cpp VLM terms.
* **Why it hurts**: Phase 2 (Architect), Phase 4 (Learner), Phase 6 (orchestrator) all depend on a
  provider abstraction. Building three bespoke integrations later is more expensive than one adapter
  now. **But** it must be a local-first adapter (llama.cpp / ollama on this box), never a cloud default,
  or the privacy guarantee in §1 of the brief is violated.
* **Task**: `llm.py` with a `Provider` protocol (OpenAI-compatible / llama.cpp server), no default
  remote endpoint, hard timeout, and a "no network egress" setting that is on by default.
* **Effort**: M. **Risk**: medium — a local LLM competes with ComfyUI for the *same* unified memory.
  This is exactly why TD-3 must land first: an agent that loads a 20 GB model next to a 20 GB WAN
  render will OOM the box.

### TD-7 · Workflow definitions have no version identity
* **Evidence**: jobs store `workflow_id`; the definition JSON is only in git (`db.py:16-41`).
* **Why it hurts**: benchmark comparisons (§C8) and "this used to work" debugging both require
  "which revision produced this output". Without it, a regenerated definition silently invalidates
  every historical timing.
* **Task**: content hash of the definition stored in `jobs.workflow_rev`, plus a `workflow_versions`
  table (hash, body, created_at). Additive migration.
* **Effort**: S-M. **Risk**: low.
* **Status (2026-11-01): RESOLVED for identity, partially for history.** `app/revisions.py` hashes
  the canonical definition (`workflow_revision`) and the built API graph (`graph_revision`); both are
  columns on `jobs` (migration v2), NULL for older rows. Rules in `docs/WORKFLOW_REVISIONS.md`,
  pinned by `tests/test_revisions.py`. Still open: a `workflow_versions` table storing the bodies, so
  an old revision can be *restored* rather than merely identified — that needs a decision on where
  definition bodies live.

### TD-8 · No migration framework; the first non-additive change is unowned
* **Evidence**: `db.py` `_ADDED_COLUMNS` + `CREATE TABLE IF NOT EXISTS`; no `schema_version`.
* **Why it hurts**: `workflow_versions`, `benchmarks`, `models`, `resources` are all new tables; a
  rename/backfill later will hit this wall. Right now it works — that is luck, not design.
* **Task**: `schema_version` table + ordered migration list with a test that migrates an empty DB and a
  seeded old DB.
* **Effort**: S. **Risk**: low. **Do it before Phase 1 tables, not after.**
* **Status (2026-11-01): RESOLVED.** `CURRENT_SCHEMA_VERSION` + `MIGRATIONS` in `app/db.py`; applied
  steps live in `schema_migrations`, mirrored to `PRAGMA user_version`; each step is idempotent by
  construction and runs in its own transaction, so a failure rolls back whole and leaves the file
  usable by the previous build. `tests/test_db_migrations.py` covers a pre-account schema, an
  account-but-no-revision schema, idempotent reopen, and a deliberately broken step. Verified against
  a copy of the production file: 130 jobs / 144 outputs / 3 users / 357 events unchanged, two columns
  added (`docs/schema-migrations.md`). Migration 3 (2026-11-01) added the `job_telemetry` ledger to that
  same production copy without touching a single existing row — the framework's first two migrations
  were both additive, so the first *non-additive* change is still untested.

### TD-9 · Frontend: one 810-line file, hand-rolled router, no component model
* **Evidence**: `dist/assets/app.js` 810 lines, `api.js` 129, `index.html` 36; no build step, no
  `package.json`.
* **Why it hurts**: the brief's "Image/Video/Audio Studio" screens either bloat this file or force a
  framework decision mid-phase. The no-build-step property is worth keeping (it is why the app is
  robust and deployable by `cp`); the monolith is not.
* **Task**: split `app.js` into ES modules (`router.js`, `views/*.js`, unchanged behaviour), keep
  `<script type="module">`, keep zero build step.
* **Effort**: M. **Risk**: low-medium (no bundler means browser must load many files — acceptable on
  loopback/LAN).

### TD-10 · Validation is structural, not type-aware
* **Evidence**: `registry.report` (183) + `_validate_required_graph_inputs:589`; `comfy.object_info`
  is available and already cached, but input *types* are never compared with the graph's values.
* **Why it hurts**: a wrong wire (e.g. an INT into a STRING input) is caught by ComfyUI at execution
  time, after a 27-minute wait — the most expensive possible failure mode.
* **Task**: a `validate_types(graph, object_info)` pass: for each `[node, idx]` link, compare declared
  output type with the consumer's required input type; report as `type_mismatch` in the validation
  response. Pure function, unit-testable without the engine (fixture from `/object_info` snapshot).
* **Effort**: M. **Risk**: low. **Highest value per line of code in Phase 2.**
* **Status (2026-11-01): RESOLVED.** `app/graphcheck.py` validates node classes, required inputs,
  literal types, combo options, link targets, link slots, link types and weight files against the
  live `/object_info`, split by execution mode (graph / host / chain). Structured issues
  (`severity`, `code`, `node_id`, `field`, `message`), 19 codes, warn-first policy with strict mode
  behind `Settings.graph_strict`. Surfaces: `GET /api/workflows/{id}/graph-check`, `checks` on the
  submit response, and `studio/tools/check_registry.py`. Measured on the shipped registry: 127
  definitions (40 graph / 82 host / 5 chain), 125 clean, 2 warnings, 0 errors
  (`docs/WORKFLOW_GRAPH_CHECK.md`). Still open: required-input *value* checking (a combo default that
  is not installed), and repair suggestions — out of scope by design (warn-first, no auto-fix).

### TD-11 · Uploads validated by extension only
* **Evidence**: `api.py:699-717` — suffix allow-list + size cap; no magic bytes, no per-user quota.
* **Why it hurts**: a `.wav` that is actually a 4 GB blob reaches ffmpeg; a crafted SVG-ish file is
  accepted as image. Local-first reduces blast radius but does not remove it (multi-user now exists).
* **Task**: magic-byte sniff (PNG/JPEG/WebP/MP4/MP3/WAV), per-user byte quota, and refuse non-media
  before writing. Detail and severity in `docs/SECURITY_REVIEW.md` S-2.
* **Effort**: S. **Risk**: low.

### TD-12 · Reproducibility: 6 pins, no lock, no hashes; vendored binaries untracked
* **Evidence**: `studio/requirements.txt` = 6 runtime + 2 test pins, `DOC` "verified on Python 3.14.4";
  `studio/tools/vision-venv`, `whisper-src` are untracked (correct) but only restorable via
  `script/install-stage-r.sh`.
* **Why it hurts**: a fresh machine rebuild depends on unpinned transitive deps and on binary downloads
  that may have moved. The README's "bootstrap from scratch" claim is therefore
  `NEEDS_VERIFICATION`, not a guarantee.
* **Task**: `requirements.lock` (pip freeze) + hashes for the pinned set; a `doctor.sh` that prints
  what is missing (engine, models, piper voice, whisper, onnx models) instead of failing at job time.
* **Effort**: S. **Risk**: low.

### TD-13 · Model catalog is hand-maintained and does not match the disk
* **Evidence** (verified in Phase 1): `registry/models_catalog.json` holds **19 records** with
  sha256/url/licence, while `models/` contains **12 weight files, 44.92 GB** (10 `.safetensors` +
  2 `.pth`). `docs/model_inventory.md` and `PROJECT_SUMMARY.md` claim 23 files / 50.54 GB — that
  number counts non-weight files (configs, `.txt`, `.json`) and is wrong either way. No LoRA, no
  ONNX model, and no GGUF is present on disk, so anything the UI advertises under those headings has
  nothing behind it. `test_model_drift.py` (8) checks definition→catalog references, not bytes.
* **Why it hurts**: the catalog is the only place licence and provenance live; drift makes it a
  suggestion rather than a source of truth.
* **Task**: `tools/catalog_audit.py` — for every file on disk, is it catalogued? for every row, is it
  present + sha256 match (on demand only, hashing 50 GB is not a default action)?
* **Effort**: S. **Risk**: low.

### TD-14 · Audio generation has a documented NaN cliff, mitigated not fixed
* **Evidence**: `DOC` ACE-Step 1.5B NaN at CFG > 1.0 and with thin/Cyrillic tags; mitigation =
  preflight warning (`registry._warn_thin_ace_tags:343`) + silence detection that fails the job
  (`jobs.py:666`).
* **Why it hurts**: the failure is loud (good) but user-facing ("your tags are bad"), and the guard is
  heuristic. A wrong-but-non-silent render still passes.
* **Task**: post-render peak/RMS check with a threshold, plus a documented "safe tag grammar" in the
  definition notes; do not attempt to fix the model.
* **Effort**: S. **Risk**: low.

### TD-15 · Capability inflation: 82 of 127 "workflows" are single ffmpeg calls
* **Evidence**: category counts by `execution` (this audit): host 82, graph 40, chain 5.
* **Why it hurts**: a UI that says "127 workflows" and a roadmap that counts them as capabilities both
  overstate the platform; it also hides the real gaps (no LoRA, no SFX, no inpaint mask UI).
* **Task**: rename in the UI to "Workflows" + "Tools", or tag `execution` visibly in the library list.
  Documentation-level fix, zero runtime risk.
* **Effort**: S. **Risk**: none.

### TD-23 · The telemetry ledger has no retention policy
* **Evidence**: `db.record_telemetry` inserts one row per terminal job; nothing prunes `job_telemetry`.
* **Why it hurts**: harmless at today's volume (a few rows a day), but this table is meant to become a
  scheduler/CostEstimator input, i.e. read on every submit. Unbounded growth turns a read that is now
  microseconds into a join over years of history.
* **Task**: a prune on `created_at` (keep N days, or keep every k-th run beyond a window) exposed as a
  maintenance action; decide the window when the estimator is designed, not before.
* **Effort**: S. **Risk**: low — but do not silently drop rows that a frozen benchmark references.

### TD-24 · Peak memory is sampled, not traced
* **Evidence**: `Sampler` polls at `interval_s` (0.5 s default) on a thread; `metrics.samples` records
  how many points exist.
* **Why it hurts**: a spike shorter than the interval is invisible, so two runs of the same graph can
  report different peaks for reasons that have nothing to do with the graph. A future estimator
  trained on these peaks inherits that noise.
* **Task**: keep the sampler as the default (cheap) but let the interval be tuned per execution type;
  when an estimator exists, weight rows by `samples` and `interval_s` instead of trusting peaks equally.
* **Effort**: S. **Risk**: none.

### TD-25 · `engine_ms` is meaningless for cached prompts
* **Evidence**: ComfyUI reports `execution_start → execution_success`; a prompt it has already run
  returns immediately with a near-zero duration.
* **Why it hurts**: a benchmark that groups by graph revision will happily average a cached 0 ms run
  with a 900 ms real one, producing a duration nobody can reproduce.
* **Task**: record whether the run was served from cache (ComfyUI's history carries no such flag — a
  `POST /history` diff or a cache-busting seed policy is needed); until then, document it and never
  average `engine_ms` without checking `execution_ms`.
* **Effort**: M. **Risk**: low (investigation only).
