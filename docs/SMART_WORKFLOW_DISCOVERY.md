# Smart Workflow Discovery

Документ описывает, как устроен поиск внешних workflow и LoRA, встроенный в существующий
ComfyUI Studio. Всё написанное ниже проверено на scratch-инстансе (`127.0.0.1:8128`) и в тестах;
там, где функциональность не проверена или ограничена, это сказано прямо.

Дата последней проверки: 2026-11-02, статусы источников сняты живыми пробами в тот же день.

---

## 1. Что это и чего это не делает

Discovery — это подсистема Studio, а не второе приложение. Она не запускает ComfyUI, не создаёт
свою базу, свой JobManager и своё хранилище workflow; она пользуется тем, что уже есть:

| Нужно | Что используется |
|---|---|
| HTTP-сервер и сессии | `backend/app/api.py`, `auth.py` (те же cookie, CSRF, роли) |
| Хранилище | существующая SQLite студии, схема 4 (аддитивные таблицы `disc_*`) |
| Модели и custom nodes | `inventory.py` (тот же инвентарь ComfyUI) |
| Свои workflow пользователя | `workflow_store.py` (`uwf_…`), `#/library` |
| Очередь генерации | `jobs.py` (импорт workflow ничего не запускает) |

Ключевое ограничение по безопасности: **импорт никогда не запускает код**. Импортированный
workflow — это файл в личной библиотеке пользователя; он появляется в ComfyUI только если
человек сам откроет его и нажмёт Queue.

## 2. Архитектура

Данные идут по одной дороге, и на каждом шаге есть точка отказа, которую можно проверить:

```
источник (сайт / API)
   │  providers/*.py — разбирают ответ провайдера в Resource
   ▼
net.py  — единственный выход в сеть: UA, таймауты, лимит 4 МБ, SSRF-гейт, robots.txt, 403/429 → RateLimited
   ▼
SyncManager (sync.py) — очередь источников, бюджет, конкурентность 1, отчёт о прогоне
   ▼
DiscoveryStore (store.py) — dedupe по content_hash/graph_sig, upsert ресурса, provenance, состояние источника
   ▼
SQLite (disc_resources, disc_links, disc_sources, disc_favorites, disc_adaptations, disc_embeddings)
   ▼
DiscoveryStore.search (search.py) + rank.py — гибридный поиск, необязательный локальный реранк
   ▼
discovery_api.py — JSON на /api/discovery/*
   ▼
frontend/dist/assets/{api.js,app.js,app.css} — экраны #/discover и #/sources
```

Модули (`backend/app/discovery/`):

| Файл | Строк | Ответственность |
|---|---|---|
| `model.py` | 316 | `Resource`, нормализация графа, `native_row()`, ключи форматов |
| `sources.py` | 159 | реестр 24 источников (`SourceSpec`) |
| `net.py` | ~250 | транспорт, лимиты, SSRF, robots.txt |
| `store.py` | ~380 | SQLite: ресурсы, provenance, состояние источников, счётчики |
| `classify.py` | 113 | тип ресурса, категория, теги |
| `media.py` | 217 | PNG/WebP-метаданные, безопасный разбор ZIP |
| `analyze.py` | 293 | разбор графа: категории, классы узлов, проверка запускаемости |
| `search.py` | ~200 | гибридный поиск, объяснение релевантности |
| `rank.py` | ~170 | необязательный локальный LLM-реранк |
| `index.py` + `embed.py` | 38 + ~130 | вектора: кэш в `disc_embeddings`, hashed n-граммы без модели |
| `adapt.py` | ~140 | типизированные операции адаптации модели |
| `sync.py` | ~180 | `SyncManager`, отчёты о прогоне, состояние источника |

| `backend/app/discovery_api.py` | ~380 | маршруты, RBAC, формы ответов |

## 3. Providers

Каждый провайдер — подкласс `BaseProvider` и обязан явно объявить, что он умеет
(`capabilities()`), а что нет: неумение выражается `UnsupportedOperation`, а не пустым
результатом. Пустой результат означает «искал, ничего не нашёл»; `UnsupportedOperation` —
«спрашивать бессмысленно», и UI показывает это разными словами.

| Провайдер | Для чего | Что реально делает |
|---|---|---|
| `github` | GitHub-репозитории | API: repo info, дерево, raw-файлы; сбор `*.json` workflow, `budget` файлов за прогон |
| `civitai` | Civitai | API метаданных моделей/LoRA, страницы как fallback; загрузка файлов не выполнялась |
| `huggingface` | HuggingFace | API моделей, поиск, workflow из README/демо-репозиториев |
| `web` | сайты-галереи | health-check + сбор ссылок со страницы; граф workflow не извлекает |
| `youtube` | видео | поиск по странице результатов, извлечение ссылок из описаний |
| `reddit` | r/comfyui, r/StableDiffusion | JSON-листинги; поиск требует OAuth |

Выбор провайдера — по `source_type` источника (`providers.build()`); тесты подменяют транспорт
(`net.set_transport`), поэтому ни один тест не ходит в сеть.

* **WORKING** — получение и обработка ресурсов проверены;
* **PARTIAL** — работает только часть функциональности;
* **REGISTERED** — источник зарегистрирован, реальное получение ресурсов не проверялось;
* **UNAVAILABLE** — источник недоступен или интеграция не работает.

**Дата проверки: 2026-11-02, 19:02–19:26 MSK** (финальный аудит перед релизным кандидатом).

### 4.1 Кто реально отдаёт workflow

Только `gh-cubiq-workflows`. Это единственный источник, который в этой проверке довёл дело
до валидного графа в базе: файлы `.json` в репозитории → скачивание → классификация
(`ui`/`api`) → граф с непустым `nodes` → provenance (`source_url`, `download_url`, commit SHA).
По этим графам работают Analyze, Compare и Adapt (Adapt строил реальные замены моделей).

### 4.2 Кто отдаёт только модели, LoRA или ссылки

* `civitai` — 20 записей на страницу, все LoRA-метаданные; workflow-типа нет ни одного;
* `huggingface` — карточки моделей; workflow не отдаёт, веса не скачиваются;
* `comfyui-org`, `comfy-workflows`, `openart`, `comfyvault`, `aigodlike`, `runcomfy`, `comfy-icu` —
  HTML-страницы, из которых достаются ссылки, но не граф.

Такие ресурсы полезны как каталог ссылок и как источник метаданных о моделях, но импортировать
из них workflow нельзя — в UI это видно по пустому Analyze.

### 4.3 Кому нужен OAuth или токен

`reddit-comfyui` и `reddit-sd`: Reddit закрывает неавторизованный доступ, оба отдают 403.
Провайдер это фиксирует как `blocked` с текстом ошибки, а не как пустой результат.
Квота GitHub без токена — 60 запросов в час, поэтому sync GitHub-источников делается
с малым `budget`; при исчерпании провайдер честно возвращает 403 и `remaining=0`.

### 4.4 Кого блокирует robots.txt

`youtube`: `robots.txt` запрещает обход для парсинга — провайдер уважает запрет и помечает
источник UNAVAILABLE. Это не поломка интеграции, а соблюдение правил сайта.

### 4.5 Чего не существует или что недоступно

* `gh-wyrde` — HTTP 404, репозитория нет (нужно либо убрать источник, либо заменить URL);
* `comfyworkflows` — TLS-ошибка при подключении с этой машины;
* `esheep` — домен не резолвится.

Два уточнения к таблице, чтобы цифры не выглядели лучше, чем есть:

* Civitai отдаёт только страницу 1 независимо от параметра `page`; провайдер это замечает,
  прекращает листание и пишет в отчёт `page 2 repeated an earlier page; stopped paging`.
  До этой правки один и тот же десяток LoRA считался трижды («scanned 60, saved 60» при 20 строках
  в базе), и отчёт выглядел убедительнее реальности.
* GitHub-источники с рабочим провайдером не прогонялись именно для проверки их собственных
  репозиториев. Статус REGISTERED — это «код есть, поведение на этом источнике не наблюдалось»,
  а не «источник плохой».

Логика статуса в UI отдельная и честная: источник, который ни разу не синхронизировали,
показывается как `never synced` (в БД `status = new`), а не как «connected».

## 5. Поддерживаемые форматы

* `ui` — граф редактора ComfyUI (`nodes`, `links`);
* `api` — prompt-формат (`{node_id: {class_type, inputs}}`).

Обе формы принимаются как есть и как обёртка в одном из ключей `graph`, `prompt`, `workflow`
(`WRAPPER_KEYS`) — метаданные обёртки сохраняются, а не выбрасываются.

Попутно разбираются:

* PNG и WebP с встроенным workflow (tEXt/iTXt-чанки, EXIF-подобные блоки);
* ZIP-архивы — только безопасно: не более 256 записей, не более 16 МБ распакованных данных,
  только разрешённые расширения (`safe_zip_entries`); zip-бомбы отбрасываются.

Лимит одного файла — `MAX_FILE_BYTES` (3,5 МБ), одного HTTP-ответа — `MAX_BYTES` (4 МБ).

## 6. Гибридный поиск

`search.py` складывает четыре независимых сигнала:

1. лексический — по названию, описанию, тегам (с нормализацией и стеммингом);
2. теги и тип ресурса (`workflow`, `lora`, `template`);
3. графовые улики — какие узлы и модели упоминает ресурс (совпадения с инвентарём);
4. вектора — косинус по эмбеддингу, если индекс построен.

Ответ на каждый результат несёт `relevance` и `explain.reasons` — список причин на человеческом
языке («совпало по названию», «тот же чекпойнт уже установлен»). Сортировка: `relevance`
(по умолчанию) или `popular` (из данных источника: `downloadCount` → `thumbsUpCount` →
релевантность). Неизвестное значение `sort` — это `400 unknown sort`, а не тихий откат.

Русский и английский: словарь синонимов (`аниме`/`anime`, `портрет`/`portrait`, `апскейл`/
`upscale`) плюс стемминг обеих сторон, поэтому «аниме портрет» и «anime portrait» дают
сопоставимый набор. Русский запрос проверен в UI на scratch-инстансе.

**Ограничение, которое нужно знать.** Семантический поиск требует модели эмбеддингов
`paraphrase-multilingual-MiniLM-L12-v2` (~470 МБ) в `~/.cache/comfyui-studio/embeddings/`.
Модели на машине нет, и она не скачивалась: до согласования используется детерминированный
fallback — hashed n-граммы (`HASH_DIM = 512`). Поэтому `semantic = false`, и UI честно пишет
«это не семантический поиск». Ставить модель — отдельное решение владельца машины.

## 7. Compatibility engine

Для ресурса считается, запустится ли он на этой установке:

| Статус | Значение |
|---|---|
| `READY` | все узлы и модели на месте |
| `PARTIAL` | часть моделей есть |
| `MISSING_MODELS` | не хватает файлов моделей |
| `MISSING_NODES` | не хватает custom nodes |
| `INCOMPATIBLE` | граф не запускается в принципе |
| `UNKNOWN` | не проверялось |

Проверка идёт по инвентарю ComfyUI (`inventory.py`, 675 узлов, 127 workflow) и по карте папок
(14 соответствий «класс узла → папка моделей»). Наличие custom nodes не предполагается:
чего нет — то названо.

## 8. Workflow analysis

`analyze.py` разбирает граф и отдаёт: категории (`t2i`, `i2i`, `upscale`, `inpaint`, `controlnet`,
`lora`, `video`, …), классы узлов с количествами, требуемые модели, «панель проверки»
(`{runnable, missing_nodes, missing_models}`) и уверенность разбора. Это данные для решения
человека, а не приговор: анализатор не блокирует импорт.

## 9. Adaptation engine

`adapt.py` предлагает замену отсутствующих моделей типизированными операциями
(`replace_model`, `drop_lora`, …). Поток: анализатор предлагает → backend отдаёт план →
**пользователь подтверждает** → `apply` применяет план на `copy.deepcopy` графа и только если
узел и слот существуют в `node_info`. Исходный ресурс не меняется, чужой workflow не меняется,
неизвестная операция — отказ.

Если замены нет, движок так и говорит: «Nothing to change … `real_esrgan_x4plus.pth` cannot be
replaced until something is installed» — это проверено в UI, а не только в тестах.

## 10. LLM-реранк

`rank.py` — необязательный второй проход локальной моделью. Правила жёсткие:

* только loopback-эндпоинт (`127.0.0.1`, `localhost`, `[::1]`, `0.0.0.0`); удалённый адрес
  отвергается с `used: false` — строки каталога не уходят с машины;
* не более 15 кандидатов (`MAX_CANDIDATES`), таймаут 45 с;
* ответ обязан быть JSON с реальными `resource_id` из запроса; выдуманные id отбрасываются
  целиком, проза вместо JSON — тоже;
* итоговая релевантность — смесь `0.5 × гибрид + 0.5 × модель`: модель может сдвинуть строку,
  но не перебить сильное лексическое совпадение.

По умолчанию реранк выключен и без локального эндпоинта не включается.

## 11. API

Все маршруты — под `/api/discovery`, все требуют сессию.

| GET | `/sources` | список источников | всем вошедшим (нужен фильтру на `#/discover`) |

| POST | `/sources` | добавить источник | admin |
| DELETE | `/sources/{id}` | удалить источник | admin |
| POST | `/sources/{id}/test` | health-check источника | admin |

| GET | `/resources/{id}` | карточка: `{resource, analysis, provenance, favorite}` — заголовок и поля ресурса лежат внутри `resource`, а не в корне ответа | всем вошедшим |
| POST | `/resources/{id}/analyze` | анализ графа | всем вошедшим |

| Действие | admin | пользователь | child |
|---|---|---|---|
| поиск, карточка, анализ, сравнение | да | да | нет (роль не активна) |
| импорт в свою библиотеку | да | да | нет |
| favorites / adaptations | свои | свои | нет |
| список источников | да | да (только чтение) | нет |
| добавить/править/удалить/тестировать источник | да | **403** | нет |
| sync | да | **403** | нет |
| re-index | да | **403** | нет |
| экран `#/sources` | да | редирект на Dashboard + «That screen is for administrators» | нет |

Проверено на scratch: у `wfuser` нет пункта Sources в навигации, прямой переход `#/sources`
уводит на Dashboard, `GET`/`POST /sync` и `POST /index` → 403, чужие favorites не видны,
чужой workflow по id — 404 на `GET`/`PATCH`/`DELETE`/`duplicate`/`open-in-editor`.
Пользовательские workflow при этом не попадают в результаты поиска discovery: они живут
в `#/library`.

## 12. Синхронизация и persistence

`SyncManager` ходит по источникам по одному (параллельных загрузок нет), бюджет — 40 файлов на
источник, до 3 страниц листинга.

Что сохраняется в SQLite для каждого источника:

* `last_sync_at` — когда закончился последний прогон;
* `status` — `ok` / `partial` / `error` / `blocked` / `unreachable` / `unsupported` / `new`;
* `last_error` — текст последней ошибки, если она была;
* `resources_count` — сколько ресурсов источника реально лежит в базе (считается по `disc_resources`,
  а не по памяти процесса);
* `rate_limit_status`, `provider`, `api_available`, `download_available`, `notes`.

Три решения, которые делают это надёжным (и три дефекта, которые были найдены и исправлены):

1. `upsert_source` — настоящий `INSERT … ON CONFLICT(source_id) DO UPDATE` с белым списком полей.
   Раньше это был `UPDATE`, который молча ничего не делал, если строки ещё не было: прогон
   «успешен», результат потерян.
2. `SyncManager.status()` при пустом состоянии процесса читает `MAX(last_sync_at)` из `disc_sources`.
   Панель больше не зависит от памяти экземпляра: после перезапуска приложения дата и статус
   остаются на месте.
3. Экран `#/sources` следит за прогоном (опрос раз в 3 с, пока `running`), затем перерисовывается
   и показывает тост с итогом. Прогон, запущенный не с этого экрана, тоже подхватывается.

Идемпотентность: повторный sync не создаёт дубликатов — ресурс опознаётся по `content_hash`
и `graph_sig`, при совпадении обновляется (`merged`), при конфликте «хуже/лучше» — правило
«never downgrade», `created_at` меняется только у новой записи. Provenance (какой источник, какой
URL, когда) сохраняется и накапливается, а не перезаписывается.

### Почему в статистике одно время стояло «1 resources stored»

Потому что счётчик честный: `resources.total` — это `COUNT(*) FROM disc_resources` текущей базы.
Единица означала, что в базе лежал один фикстурный ресурс: dev-инстанс `scratch_discovery.py`
при старте пересоздаёт каталог (`shutil.rmtree`), и результаты предыдущего sync вместе с базой
исчезали. В рабочем инстансе и в тестах счётчик совпадает с содержимым: после реального sync
на чистой базе он показывает 37 (1 фикстура + 36 из GitHub), а после второго прогона — те же 37,
потому что повторы уходят в `merged`. Чтобы проверять persistence без потери базы, у скрипта
появился режим `SCRATCH_KEEP=1`.

## 13. Ограничения и известные пробелы

Честный список на 2026-11-02:

* **Семантический поиск не включён** (нет модели эмбеддингов — скачивание не согласовано).
* **Синхронизирован только один источник** (GitHub cubiq). Остальные 8 GitHub-источников
  с рабочим провайдером не прогонялись: их статус — REGISTERED, а не WORKING.
* **Недоступны 6 источников из 24**: `comfyworkflows` (TLS), `esheep` (DNS),
  `youtube` (robots.txt), `gh-wyrde` (404), `reddit-comfyui` и `reddit-sd` (403 без OAuth).
  `runcomfy`, `comfyui-org` и `comfy-icu` в предыдущем снимке значились по таймауту,
  в проверке 2026-11-02 отвечают и потому переведены в REGISTERED/PARTIAL — это доступность,
  а не доказанная работоспособность провайдера.
* **web-провайдер не извлекает граф** из HTML-галерей — только ссылки. Поэтому такие источники
  PARTIAL, даже когда хост отвечает.
* **Coverage по discovery неровный**: `media.py` ~51 %, `rank.py` был 16 % (добавлены тесты на
  loopback-гейт и разбор ответа), `providers/web.py` ~54 %. Покрытие не выдаётся за проверку.
* **`0.0.0.0` в списке loopback-хостов реранка** — на Linux это локальный адрес; при переносе
  на другую ОС список нужно перечитать.
* **ZIP-путь назван `safe_zip_entries`**, а не `read_archive`; покрытие частичное.
* **Ссылка «Open in ComfyUI»** ведёт на `editor_port` (8189); на этой машине loopback:8189
  не слушает, редактор доступен только с `192.168.31.60`.
* **Сравнение двух локальных workflow каталога** не поддерживается — сравниваются
  локальный и найденный ресурс.
* **Названия находок** строятся по строгому приоритету: имя из метаданных workflow →
  имя файла в репозитории → прочие метаданные → заголовок первого узла графа.
  Заголовок узла — самый последний вариант, иначе два разных файла одного репозитория
  называются одинаково («CLIP Text Encode (Positive)»). Регрессия закреплена в
  `backend/tests/test_discovery_titles.py`.
* **Discovery в production ещё не наполнялся**: база production пуста (0 ресурсов),
  вся проверка шла на отдельном инстансе и временных БД. Первый реальный прогон
  в production — отдельное решение владельца.
* **SSRF и robots.txt** закрыты кодом и тестами (`test_discovery_net_guards.py`, 20 тестов):
  `net.check_public_url()` отвергает loopback, LAN, link-local и `169.254.169.254`, а также
  имена, которые в них резолвятся; `robots.txt` спрашивается перед загрузкой HTML-страниц
  (web-галереи, поиск YouTube) и кэшируется на час. Против настоящих сайтов это не проверялось:
  GitHub/S3-API вызываются как API, а не как краулинг, и robots.txt для них не запрашивается.

## 14. Вёрстка и адаптивность

Проверено в браузере на 1440×900, 834×1112 и 390×844 (не «на глаз», а замерами
`scrollWidth − clientWidth` и геометрии элементов):

* `.shell` использует `minmax(0, 1fr)` — широкая таблица источников прокручивается внутри себя,
  а не растягивает страницу (было: страница шириной 1240 px на экране 390 px);
* мобильные фильтры — строка, а не колонка: колоночный flex превращал `flex: 1 1 180px`
  в поле поиска высотой 180 px (треть экрана);
* **на телефоне вторичные фильтры свёрнуты под кнопку `Filters`** (порог 700 px).
  Видны всегда только поле поиска, кнопка **Search** и сама кнопка `Filters` с числом
  включённых фильтров; тип, категория, источник, базовая модель, «только совместимые»,
  scope и сортировка раскрываются по нажатию. Свёрнутое состояние — действие в интерфейсе,
  а не потеря данных: фильтры и последняя выдача остаются, панель не делает запрос
  при раскрытии, а выбор пользователя запоминается до конца сессии вкладки;
* на десктопе обёртка вторичных фильтров прозрачна для раскладки (`display: contents`),
  поэтому тулбар выглядит ровно как раньше, а кнопка `Filters` скрыта;
* форма добавления источника стоит на своей строке и не разъезжается (URL 320 px + имя 220 px
  + кнопка), на телефоне — в столбик;
* карточки результатов — одна колонка на телефоне, сетка на планшете и десктопе;
* горизонтального скролла на всех трёх ширинах нет (`overflow: 0`).

Навигация на телефоне по-прежнему остаётся вертикальным списком сверху — это поведение
существующей студии, а не новое; гамбургер-меню не добавлялось.

### Чужие карточки и свои workflow в одной выдаче

Поиск ищет и по внешним источникам, и по локальному каталогу. У локальной карточки нет
discovery-записи, поэтому кнопки `Analyze`, `Compare` и `Favourite` отвечали на неё
«no such resource», а `Analyze` оставлял в карточке вечную надпись «Checking…».
Теперь у локальной строки действия discovery не показываются вообще — вместо них ссылка
**Open in the library** (`#/library`); у найденного ресурса набор прежний (`Analyze`, `Compare`, `Import`,
`Adapt`, `Favourite`). Если `Analyze` всё же падает, карточка показывает текст ошибки,
а не остаётся в состоянии «Checking…».

### Если поиск отвергнут

Раньше любой ответ 4xx от `/api/discovery/search` заменял весь раздел текстом ошибки —
вместе с фильтрами и уже найденными результатами. Теперь ошибка показывается полосой
рядом с полем поиска и означает ровно то, что случилось:

| Статус | Что видит пользователь |
|---|---|
| 400 | «The search was rejected — check the filters and try again» + текст сервера (`unknown sort: …`) |
| 401 | «Your session has expired. Reload the page and sign in again» |
| 403 | «You are not allowed to search this catalogue» |
| 429 | «Too many searches in a row. Wait a moment and try again» |
| 500 / 502 / 503 | «The server failed while searching. Nothing was lost» / «not answering» / «busy» |
| сеть недоступна | «The server could not be reached» |

При этом на экране остаётся предыдущая успешная выдача с подписью, что она из прошлого
запроса, все фильтры сохраняются, а кнопка **Try again** повторяет ровно тот же запрос.
Роутинг не ломается: раздел остаётся на месте, `#/discover` никуда не уводит.


## 15. Инструкция пользователя

1. Войдите в Studio. Пункт **Find workflows** (`#/discover`) доступен всем.
2. Введите запрос по-русски или по-английски, при необходимости сузьте фильтрами
   (тип, категория, источник, базовая модель, «только совместимые») и отсортируйте по
   релевантности или популярности.
3. На карточке: **Analyze** — что внутри и чего не хватает; **Favorite** — сохранить;
   **Import** — скопировать в свои workflow (появится в `#/library`, ничего не запускается);
   **Adapt** — предложить замену отсутствующих моделей и применить её после подтверждения.
4. Отметьте две карточки и нажмите **Compare**, чтобы увидеть различия графов.
5. Администратор в **Sources** (`#/sources`) видит 24 источника, их настоящий статус, дату
   последней синхронизации и число сохранённых ресурсов. **Test** проверяет доступность,
   **Sync** запускает прогон (прогресс виден на странице, итог — тостом), **Re-index**
   пересобирает вектора.

Что означает пустой результат: если совпадений нет — это не ошибка поиска; проверьте фильтры
(«только совместимые» и выбранный источник сужают сильнее всего).
