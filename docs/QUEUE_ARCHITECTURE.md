## 1. Что есть сегодня (измерено)

### 1.1 Одна очередь, один worker

`JobManager` (`app/jobs.py`) держит:

| Поле | Строка | Что это |
|---|---|---|
| `_queue: asyncio.Queue[str]` | `jobs.py:81` | одна очередь job-id, порядок = порядок `POST /api/jobs` |
| `_worker: asyncio.Task` | `jobs.py:82` | **один** цикл `_worker_loop`, создаётся в `start()` (`jobs.py:112`) |
| `_running_job: str \| None` | `jobs.py:86` | одно поле на весь процесс — предполагает ровно одну задачу в полёте |
| `_progress`, `_stage`, `_checks`, `_engine_ms`, `_mono` | `jobs.py:83-100` | словари по `job_id`, конкурентности не мешают |
| `_cancelled`, `_interrupt_requested` | `jobs.py:85,87` | множества `job_id`, тоже не мешают |

`_worker_loop` (`jobs.py:389-414`) ждёт `queue.get()`, вызывает `_run_job`, в `finally` пишет
телеметрию и `task_done()`. Пока задача в полёте, следующая не начинается **никогда** — вне
зависимости от типа исполнения.

`settings.one_at_a_time = True` (`config.py:51`) объявлен, но **ни в одном месте не читается**:
проверено `grep -rn one_at_a_time` — только объявление и комментарий в докстринге `jobs.py:6`.
Последовательность обеспечивается структурой (один worker), а не настройкой.

### 1.2 Три типа исполнения

`execution` в определении workflow (`app/schemas.py`), фактическое распределение по
`studio/registry/workflows` (посчитано скриптом по 128 JSON-файлам):

| `execution` | Сколько | Что делает | Где в коде |
|---|---|---|---|
| `graph` | 40 | POST `/prompt` в ComfyUI, ожидание `/history`, WS-прогресс | `jobs.py:515-604` |
| `host` | 82 | `asyncio.to_thread(hosttools.run_host_tool, …)`: piper, ffmpeg, Pillow | `jobs.py:497-499, 606-665` |
| `chain` | 5 | сначала host-инструмент, затем graph с его выходом | `jobs.py:503-513` |

82 host-инструмента не трогают видеопамять вообще: они запускают внешние бинарники через
`subprocess.run` (`hosttools.py:70-86`) в отдельном vision-venv, а ffmpeg/Pillow работают на CPU.
Именно это и делает текущую схему дорогой: 2-секундная миниатюра ждёт 27-минутный Wan-рендер
(TD-4, `docs/TECHNICAL_DEBT.md`).

### 1.3 Цепочки — не «ещё один host tool»

Все пять цепочек устроены одинаково и измерены по определениям:

| id | host-фаза | `chain_bind` | `timeout_s` |
|---|---|---|---|
| `sam-bg-replace` | `sam_segment` | node `4` ← `image` | 600 |
| `sam-region-restyle` | `sam_segment` | node `4` ← `image` | 900 |
| `sam-object-remove` | `sam_segment` | node `4` ← `image` | 600 |
| `cn-dual-canny-depth` | `depth_map` | node `4` ← `image` | 600 |
| `cn-depth-sdxl` | `depth_map` | node `4` ← `image` | 900 |

Фактическая механика (`jobs.py:503-513` + `hosttools.run_sam_segment` / `run_depth_map`):

1. host-инструмент считает маску/карту глубины на CPU (ONNX, vision-venv), пишет PNG **дважды**:
   в `output/…/studio/` (как результат) и в `ComfyUI/input/` (как вход для графа);
2. `comfy_input` из результата подставляется в `chain_bind.node.chain_bind.input`
   (`registry.validate_and_build(..., chain_input=…)`);
3. граф уходит в тот же ComfyUI через тот же `client.submit`.

То есть chain — это **host-препроцессор, за которым обязательно идёт GPU-граф**. Никакой
цепочки без GPU-фазы в реестре нет: `graphcheck.py:341-359` требует `chain_bind`, а
`registry.py:136-150` отказывается загружать chain без него.

### 1.4 Отмена

`cancel()` (`jobs.py:274-307`):

* `queued` → `finish_job(..., "cancelled")` + строка телеметрии сразу же (`jobs.py:288-295`);
  worker увидит id в `_cancelled` и молча пропустит (`jobs.py:395-399`);
* `submitted` / `running` → `client.interrupt()` (`POST /interrupt` в ComfyUI) + флаг в
  `_interrupt_requested`; worker по завершении опроса трактует это как `cancelled`
  (`jobs.py:569-583`).

**Измеренный дефект, который конкурентность превратит в регрессию:**
`interrupt()` останавливает текущий граф ComfyUI, кем бы он ни был запущен. Для host-задачи это
значит: (а) сама задача не останавливается — `run_host_tool` крутится в потоке до конца
таймаута, job в итоге завершится `completed`; (б) при двух контурах `interrupt` попадёт в
**чужой** GPU-job, который сейчас держит движок. Один пользователь нажмёт «отменить» на
миниатюре — умрёт чужой рендер. Это надо чинить в том же шаге, иначе шаг 4 создаёт новую
возможность убивать соседей.

### 1.5 Reconcile после рестарта

`reconcile_orphans()` (`jobs.py:129-170`): берёт `db.unfinished_job_ids()`, спрашивает
`client.queue()`; job, чей `prompt_id` ещё в `queue_running`/`queue_pending`, **усыновляется**
(остаётся как есть), остальные → `interrupted` + строка телеметрии. При недоступном движке не
трогает ничего (`jobs.py:143-147`) — это правильно и должно сохраниться.

Следствие, которое надо назвать честно: у host-задачи `prompt_id` не бывает никогда, поэтому
host-job, застигнутый рестартом, **всегда** становится `interrupted`. Так было и до шага 4, и
так останется: доказать, что ffmpeg-процесс жив, нечем — процесс принадлежит не нам.

### 1.6 БД и транзакции

`Database` (`db.py:203-221`): **одно** соединение `sqlite3` с `check_same_thread=False`,
`RLock`, `journal_mode=WAL`, `synchronous=NORMAL`, `foreign_keys=ON`. Каждый публичный метод
берёт `self._lock` на время операции и коммитит внутри. Миграции — `BEGIN IMMEDIATE` на шаг
(`db.py:251-263`).

Что это значит для нескольких worker:

* **гонок SQL нет** — все записи сериализованы одним RLock;
* **но** вызовы синхронные из event loop: 4 потока, каждый пишет строку раз в 2 с, дают
  микросекундные блокировки — не проблема; проверять надо измерением, а не верой;
* `task_done()`/`join()` в очереди не используются, поэтому второй worker не ломает счётчики.

### 1.7 Телеметрия и benchmark ledger

`ExecutionTelemetry` (`telemetry.py:426+`): `begin(job_id)` поднимает `Sampler` на задачу,
`record()` пишет строку в `job_telemetry` (`INSERT OR REPLACE`, `db.py:642-659`).
Память — системная: `MemTotal − MemAvailable`, `available_min_mb` — минимум за прогон
(`telemetry.py:37-40`). `engine_ms` пишется только для `graph`/`chain`.

**Ограничение, которое появляется при конкурентности:** два одновременных job сэмплируют один и
тот же `/proc/meminfo`. Пики перестают быть атрибутируемыми: обе строки покажут один и тот же
общесистемный пик. Схему БД ради этого не меняем — в `metrics` (JSON-блоб) добавляются
`lane` и `max_concurrent_host`, чтобы строка сама говорила, в каком режиме её снимали.

### 1.8 Потребители API и фронтенд

* `GET /api/stats` (`api.py:482-509`) возвращает `snapshot()` **плюс** счётчики из БД:
  `queue_depth`, `running`, `worker_alive`, `cancelling`, `my_queued`, `max_per_user`,
  `queued`, `running`, `completed`, `failed`, `comfy_queue_running/pending`.
* `GET /api/jobs` (`api.py:753-766`) — список + `snapshot`.
* `GET /api/jobs/{id}` — `stage` из памяти менеджера (`api.py:775`).
* Фронтенд (`frontend/dist/assets/app.js:471,544`) использует `queue_position` и `duration_s`;
  `snapshot` целиком не разбирает. Значит имена ключей `snapshot` менять нельзя, а добавлять
  новые — можно.
* Квоты: `max_queue_depth` считается по `db.count_jobs("queued")` (`jobs.py:192`), персональный
  лимит — `db.active_jobs_for(user_id)` = queued+submitted+running (`jobs.py:199-205`). Оба
  счётчика **уже** глобальные по всем типам исполнения — делить их по контурам не нужно и нельзя,
  иначе один человек обойдёт лимит, чередуя host и graph.

## 2. Целевая архитектура

Один `JobManager`, одна таблица `jobs`, одна очередь приёма, **два исполнительных контура**.

```
POST /api/jobs ──► submit()  (валидация, preflight, квоты — без изменений)
                     │
                     ├─ row(status=queued) в SQLite          ← единый жизненный цикл
                     └─ _order.append(job_id); wake.set()    ← единый порядок приёма
                              │
                    ┌─────────┴──────────────────────────────┐
                    │  _dispatcher (одна корутина)           │
                    │  сканирует _order с начала:            │
                    │   host  → CPU pool, слот есть?         │
                    │   graph → GPU lane, слот есть?         │
                    │   chain → GPU lane (целиком)           │
                    │  нет слота → остаётся в _order         │
                    └───────┬────────────────────┬───────────┘
                            │                    │
                  CPU HOST POOL (N=2)     GPU SERIAL LANE (1)
                  asyncio.Semaphore(N)    asyncio.Semaphore(1)
                  run_host_tool в потоке   submit → ComfyUI → /history
                            │                    │
                            └────────┬───────────┘
                              общий _run_job → finish_job → telemetry
```

Почему диспетчер, а не «два потребителя одной `asyncio.Queue`»: один `asyncio.Queue` нельзя
раздать двум контурам, не потеряв порядок и не начав head-of-line blocking. Диспетчер со
сканированием `_order` даёт обе гарантии одновременно: FIFO **внутри** контура и отсутствие
простоя — host-job за стоящим GPU-job стартует сразу, а не после него.

### 2.1 Инварианты (обязательные, проверяются тестами)

| # | Инвариант | Чем держится |
|---|---|---|
| I1 | Один Job ID, один жизненный цикл | тот же `jobs` row, тот же `_run_job` |
| I2 | Не более **одного** GPU-графа одновременно | `_gpu_sem = Semaphore(GPU_MAX_CONCURRENT)` = 1 |
| I3 | Host-конкурентность ≤ `CPU_HOST_WORKERS` | `_host_sem = Semaphore(N)` |
| I4 | Chain не обходит GPU lane | chain не имеет своего контура; слот GPU берётся на **всю** задачу |
| I5 | Квоты и `max_queue_depth` — глобальные | `db.count_jobs("queued")`, `active_jobs_for()` не меняются |
| I6 | Отмена не задевает соседей | `interrupt()` только для владельца GPU-слота |
| I7 | Reconcile не создаёт дубликатов | `reconcile_orphans` не меняется: он работает по БД и `/queue` |
| I8 | Ни одна задача не теряется при рестарте | row в БД до постановки; диспетчер стартует по `_order` из `unfinished_job_ids()` |
| I9 | API-совместимость | ключи `snapshot` сохраняются, добавляются новые |

### 2.2 Жизненный цикл и переходы состояний

Статусы не меняются. Меняется только то, кто и когда их выставляет.

| Из | В | Кто | Условие |
|---|---|---|---|
| — | `queued` | `submit()` | row создан, id в `_order` |
| `queued` | `queued` (ждёт) | диспетчер | нет свободного слота своего контура или MemAvailable ниже порога |
| `queued` | `cancelled` | `cancel()` | владелец/админ, до старта; id остаётся в `_order`, диспетчер его пропускает |
| `queued` | `submitted` | worker | взят слот: graph/chain |
| `queued` | `running` | worker | взят слот: host (у него нет фазы `submitted`) |
| `submitted` | `running` | `_run_job` | ComfyUI вернул `prompt_id` |
| `submitted`/`running` | `cancelling` | `cancel()` | только для задачи, держащей GPU-слот |
| `running` | `completed` | worker | outputs записаны |
| `running` | `failed` | worker | ошибка инструмента/движка/графа |
| `running` | `cancelled` | worker | `_interrupt_requested` (graph) или флаг хоста |
| любой незавершённый | `interrupted` | `reconcile_orphans` | рестарт, движок подтвердил, что графа нет |
| `completed`/`failed`/`cancelled` | `queued` (новая row) | `POST /rerun` | всегда новый job id |

Освобождение слота — **только** в `finally` задачи контура, до записи телеметрии: иначе
следующая задача может занять слот и попасть в телеметрию раньше, чем закрыта предыдущая.

### 2.3 Конфигурация

| Setting | Значение по умолчанию | Смысл |
|---|---|---|
| `cpu_host_workers: int` | `2` | слотов CPU-пула; `0` = пул выключен (диагностика: host идёт в GPU lane, как сегодня) |
| `gpu_max_concurrent: int` | `1` | **не** редактируется из UI; при значении >1 приводится к 1 с записью в events (движок один, второй граф сломает модель) |
| `cpu_host_min_available_mb: int` | `1024` | порог `MemAvailable` для допуска host-задачи; `0` = без ограничения |
| `cpu_host_admission_poll_s: float` | `5.0` | период перепроверки допуска, пока пул заблокирован по памяти |

Все три — обычные поля `Settings`, читаются из JSON-конфига `studio/config/studio.json` и из env
(`STUDIO_CPU_HOST_WORKERS`, `STUDIO_CPU_HOST_MIN_AVAILABLE_MB`). `cpu_host_workers` попадает в
`EDITABLE_FIELDS` (админ может менять из UI, применяется к следующему циклу диспетчера без
рестарта). `gpu_max_concurrent` — **не** попадает.

Проверяемые конфигурации: `1`, `2`, `4` worker, `0` (выключен).

### 2.4 Chain: решение

**Chain исполняется целиком в GPU-контуре.** Обоснование, а не вкус:

1. GPU-фаза у chain есть всегда (все 5 определений имеют `chain_bind` + GPU-граф) — значит chain
   по определению занимает GPU;
2. host-фаза chain пишет PNG в `ComfyUI/input/` и передаёт имя графу: разнести фазы по разным
   контурам можно, но тогда между ними job держит два плохо совместимых состояния (частичный
   результат, ожидание графа) — это переработка chain-executor'а, а не настройка очереди;
3. текущее поведение (chain держит единственный worker от начала до конца) сохраняется буквально;
4. обойти GPU-очередь через chain нельзя: слот GPU берётся один раз на всю задачу.

**Остаточная цена решения, названная честно:** chain с медленной host-фазой (SAM ViT-B, до 900 с
таймаута) блокирует GPU-контур на всё это время, как блокирует и сегодня. Это не регрессия, но и
не улучшение. Более тонкое разделение (host-фаза в пуле, GPU-фаза по слоту, job в состоянии
`preprocessing`) вынесено в отдельное предложение — см. §5, пункт `CHAIN-SPLIT`, и **не** делается
в этом шаге.

### 2.5 Отмена в двух контурах

* **GPU-задача** — как сейчас: `POST /interrupt`, флаг, `cancelling` → `cancelled`. Дополнительно:
  `interrupt()` разрешён **только** если `job_id` держит GPU-слот (`_gpu_holder == job_id`).
  Проверка под той же блокировкой, что и захват слота, — иначе гонка «отменил между проверкой и
  отправкой».
* **Host-задача** — новый кооперативный механизм: `cancel()` ставит флаг в
  `_host_cancel[job_id]`; `run_host_tool` получает callback `should_stop()` и превращает
  `subprocess.run` в `Popen` + опрос с `terminate()` (SIGTERM, затем SIGKILL по таймауту).
  Это чинит и сегодняшний дефект (host-job сейчас не отменяется вовсе), и защищает GPU-job
  соседа от чужого `interrupt`.
* **Queued** — как сейчас, без изменений.
* **Shutdown** — `stop()` отменяет задачи контуров; host-процессы получают `terminate()` через тот
  же механизм; `reconcile_orphans` на следующем старте доводит записи. Утечки потоков: задачи,
  запущенные `asyncio.to_thread`, неотменяемы — поэтому остановку надо делать **через флаг
  инструмента**, а не только `task.cancel()`.

## 3. Риски

| # | Риск | Вероятность | Как снимаем |
|---|---|---|---|
| R1 | `interrupt` убивает чужой GPU-job при отмене host-задачи | была 100 % при появлении конкурентности | `interrupt` только владельцу GPU-слота; host-отмена — флаг + `terminate` |
| R2 | Коллизия имён файлов: `_unique_target`/`_unique_pair` (`hosttools.py:40,339`) — проверка «свободно?» и запись не атомарны; два потока одного инструмента выберут одно имя | высокая | резервировать имя атомарно (`O_CREAT\|O_EXCL`), при занятости — следующий номер; тест на 2 параллельных `piper_tts` |
| R3 | Пики памяти в телеметрии перестают быть атрибутируемыми | 100 % | схема v3 не меняется; `lane` + `max_concurrent_host` в `metrics`; в документации сказано прямо |
| R4 | SQLite: 4 конкурентных писателя | низкая (RLock) | нагрузочный тест 4×50 записей; при необходимости — `busy_timeout` и один writer-поток |
| R5 | `queue_position` меняет смысл (глобальный порядок приёма) | средняя | позиция = индекс в `_order`; слоты контуров не влияют на порядок; фронтенд читает только это поле |
| R6 | Голодание: непрерывный поток host-job'ов не пускает GPU-job | средняя | диспетчер сканирует с начала `_order`, а не «сначала свой контур»; при равном порядке GPU-job впереди по индексу |
| R7 | Долгая host-фаза chain держит GPU-слот | 100 %, но не регрессия | задокументировано; отдельное предложение `CHAIN-SPLIT` |
| R8 | Утечка потоков/процессов при shutdown | средняя | `terminate` по флагу, ожидание задач контуров с таймаутом, тест «после stop() нет живых ffmpeg» |
| R9 | Висящие задачи: диспетчер ждёт слот, задача отменена | низкая | пропуск терминальных id при сканировании; тест «отмена ждущего не вешает очередь» |
| R10 | Гонка статусов: `cancel()` и `finish_job()` одновременно | низкая | `finish_job` в БД — единственный писатель терминального статуса; `cancel` для running только ставит флаг |
| R11 | Настройка `gpu_max_concurrent > 1` попадёт в конфиг | средняя | клампится к 1 при загрузке и при `PUT /api/settings` (поле не редактируемое), событие в лог |
| R12 | Host-инструменты делят `ComfyUI/input/` с движком | низкая | уникальные имена (см. R2); граф читает только своё имя |

## 5. Открытые вопросы к владельцу

1. **`CHAIN-SPLIT`** — выносить ли разделение host/GPU фаз chain в отдельную задачу (сейчас
   предлагается не делать)? Цена отказа: 5 цепочек продолжают держать GPU на время препроцессинга.
2. **Порог памяти** — `cpu_host_min_available_mb = 1024` достаточно консервативен? На этой машине
   `MemAvailable` держится около 20 ГБ, SAM ViT-B ≈ 1–2 ГБ, ffmpeg concat 4 видео — сотни МБ.
3. **Дефолт `cpu_host_workers = 2`** — оставляем 2 (как в ТЗ), или ставим 3 при 32 ядрах? В ТЗ
   сказано 2, поэтому по умолчанию 2; 4 проверяется тестом и бенчмарком.

## 6. Стратегия тестирования (что доказывается)

Все тесты — на `FakeClient` и на фейковых host-инструментах с управляемыми задержками; GPU не
нужен, реальные ffmpeg-прогоны — только в бенчмарке.

| Требование | Тест |
|---|---|
| два host job одновременно | 2 host-job по 0.3 с, `cpu_host_workers=2`, суммарное время < 0.55 с и `max_parallel == 2` |
| третий ждёт | 3 host-job, `workers=2`, третий стартует только после освобождения слота |
| GPU строго последовательно | 3 graph-job, `max_parallel_gpu == 1`, порядок = порядок приёма |
| host не блокирует GPU | graph-job + host-job одновременно на разных контурах |
| GPU не блокирует pool | пока graph в полёте, 2 host-job завершаются |
| chain не обходит GPU | 2 chain-job: их GPU-фазы не пересекаются; `chain` никогда не в host-пуле |
| отмена одной не трогает соседей | отмена running host-job при живом graph-job: `fake.interrupted == 0`, сосед завершается `completed` |
| ошибка worker не роняет пул | host-job бросает исключение → `failed`, следующий выполняется |
| restart/reconcile без дубликатов | `unfinished_job_ids()` + повторный `start()` → одна row, одна telemetry-строка |
| телеметрия: queue wait / execution | строка содержит ненулевые `queue_wait_ms` и `execution_ms`, `timing_source=monotonic`, `lane` в `metrics` |
| SQLite при конкурентных записях | 4 задачи × 50 записей, `PRAGMA integrity_check = ok`, ни одна строка не потеряна |
| shutdown | после `stop()` нет живых задач контуров и запущенных host-процессов |
| конфигурации 1/2/4/0 | параметризованный тест: `cpu_host_workers ∈ {1,2,4,0}`, наблюдаемая параллельность ≤ N; при 0 host идёт в GPU lane |

Матрица реализована в `studio/backend/tests/test_queue_lanes.py` (22 теста), плюс атомарный резерв
в `tests/test_hosttools.py`. Полный regression на итоговом дереве: **497 passed, 0 failed**, 48.2 s;
покрытие **76.0 %** (было 75.2 %), `jobs.py` 78 %, `telemetry.py` 92 %, `hosttools.py` 63 %.

## 7. Бенчмарк — измерено

Инструмент: `studio/backend/tools/queue_benchmark.py`. Работает на **временной БД и временном
output-дереве**, продовый `studio/data/studio.db` не открывается, в пользовательскую папку ничего
не пишется. GPU-фаза опциональна (`--with-graph`) и отказывается стартовать, если в очереди
ComfyUI уже есть работа.
